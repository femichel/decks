1.3
TSO
Definición

La virtualización crea una capa de abstracción entre el hardware físico y los sistemas operativos que lo usan, permitiendo que varias máquinas virtuales compartan un mismo host de forma aislada.

Cada máquina virtual (VM) "cree" que tiene su propio procesador, memoria, disco y tarjeta de red — aunque en realidad todos esos recursos están siendo repartidos y programados por una capa de software llamada hipervisor.

1.3.1
TSO
1.3.1 Componentes

Las cuatro piezas del modelo

Host — el servidor físico: CPU, RAM, disco y NIC reales.

Hipervisor (VMM) — el software que crea, programa y aísla las VM; reparte los recursos del host entre ellas.

Guest — cada sistema operativo invitado que corre dentro de una VM, sin saber que el hardware es virtual.

Recursos virtualizados — vCPU, memoria asignada, disco virtual (vmdk/qcow2) y adaptadores de red virtuales.

1.3.1
TSO
1.3.1 Niveles de virtualización

Dos niveles de hipervisor

Tipo 1 — Bare metal
  • Corre directamente sobre el hardware, sin SO anfitrión de por medio.
  • Mejor rendimiento y menor latencia: es la norma en centros de datos.
  • Ejemplos: VMware ESXi, Microsoft Hyper-V (rol de servidor), KVM, Citrix XenServer.
  • Uso típico: servidores de producción, nubes privadas y públicas.
Tipo 2 — Hospedado
  • Corre como una aplicación sobre un sistema operativo anfitrión ya instalado.
  • Más fácil de instalar; overhead adicional por la capa del SO anfitrión.
  • Ejemplos: VirtualBox, VMware Workstation/Fusion, Parallels.
  • Uso típico: laboratorios, desarrollo local, pruebas del aula.

1.3.2 VPS

Un VPS (Virtual Private Server) es una máquina virtual que un proveedor de hosting o nube te renta con recursos garantizados y acceso root/administrador propio.

Es la unidad comercial más común de la nube IaaS: EC2 de AWS, Compute Engine de GCP y las VM de Azure son, técnicamente, VPS gestionados a gran escala sobre hipervisores Tipo 1.

1.3.2
TSO
1.3.2 VPS en el espectro del hosting

¿Por qué elegir un VPS?

Compartido
  • Recursos y kernel compartidos entre cientos de cuentas
  • Sin acceso root
  • Costo muy bajo
VPS
  • Recursos garantizados por VM
  • Acceso root/administrador completo
  • Escalable bajo demanda
Dedicado
  • Hardware físico exclusivo
  • Máximo rendimiento y costo
  • Sin flexibilidad de escalado inmediato

Ejemplo resuelto

Aprovisionar una VM con VBoxManage

bash — host de laboratorio
# 1. Crear la definición de la VM
$ VBoxManage createvm --name "srv-debian-01" --ostype Debian_64 --register

# 2. Asignar recursos: 2 vCPU, 2048 MB de RAM
$ VBoxManage modifyvm "srv-debian-01" --cpus 2 --memory 2048 --nic1 nat

# 3. Crear y adjuntar disco virtual de 20 GB
$ VBoxManage createmedium disk --filename srv-debian-01.vdi --size 20480
$ VBoxManage storagectl "srv-debian-01" --name SATA --add sata
$ VBoxManage storageattach "srv-debian-01" --storagectl SATA --port 0 --medium srv-debian-01.vdi

# 4. Montar el ISO de instalación y arrancar
$ VBoxManage storageattach "srv-debian-01" --storagectl SATA --port 1 --type dvddrive --medium debian-12.iso
$ VBoxManage startvm "srv-debian-01"
VM "srv-debian-01" ha sido iniciada correctamente.

Caso de estudio

Cuando el aislamiento falla

Incidente real

Las vulnerabilidades Meltdown y Spectre (2018) explotaron la ejecución especulativa del procesador para leer memoria fuera de los límites asignados a una VM — rompiendo, a nivel de hardware, el aislamiento que el hipervisor debía garantizar entre distintos inquilinos de un mismo servidor físico.

En un entorno multi-tenant de nube pública, una VM comprometida pudo en teoría leer datos de la VM vecina, sin haber vulnerado al hipervisor directamente.

Consecuencia para administradores de infraestructura: los parches del hipervisor y del microcódigo del CPU son tan críticos como los del propio sistema operativo invitado.

Instalar y configurar una VM

Individual Duración estimada: 50 min · Entregable: reporte + captura
  1. Instala VirtualBox o el hipervisor Tipo 2 asignado por el docente.
  2. Crea una VM con 2 vCPU, 2 GB de RAM y 20 GB de disco.
  3. Instala una distribución Linux ligera (Debian o Ubuntu Server) desde ISO.
  4. Configura red en modo bridge y verifica conectividad con ping hacia el host.
  5. Documenta cada paso con capturas de pantalla en un reporte de instalación.
Criterios de evaluación: VM funcional y accesible por red (40%) · reporte completo con evidencia (30%) · justificación de los recursos asignados (30%).

Desde la práctica profesional

Errores frecuentes al dimensionar VM

Error común
  • Sobreasignar vCPU "por si acaso" y degradar el planificador del hipervisor.
  • Usar discos de aprovisionamiento fijo en laboratorio, agotando espacio del host.
  • No aislar la red de administración de la red de la VM invitada.
Buena práctica
  • Dimensionar vCPU según carga real medida, no por intuición.
  • Usar discos de aprovisionamiento dinámico (thin) en entornos no productivos.
  • Separar VLAN de gestión y VLAN de datos desde el diseño inicial.

Cierre

En cinco ideas

  • La virtualización abstrae el hardware físico para que varias VM lo compartan aisladas entre sí.
  • El hipervisor Tipo 1 corre bare metal; el Tipo 2 corre sobre un SO anfitrión.
  • Existen niveles de virtualización más allá del hardware: SO, aplicación y almacenamiento.
  • Un VPS es una VM comercial rentada con recursos garantizados — base de la nube IaaS.
  • El aislamiento entre VM no es absoluto: requiere parches de hipervisor y de firmware.
