Activación

Tu servidor tiene 4 núcleos, pero corre 200 procesos a la vez. ¿Cómo es posible?

El SO no ejecuta 200 procesos simultáneamente en sentido literal: reparte el tiempo de CPU entre ellos a una velocidad que hace parecer que corren en paralelo. Ese reparto tiene reglas — y hoy las vas a entender.

Definición

Un programa es código estático en disco; un proceso es ese programa en ejecución, con su propio espacio de memoria, registros y estado.

Cuando ejecutas nginx, el binario en disco es el programa; cada instancia corriendo en RAM, con su PID propio, es un proceso.

1.2 Proceso

Cómo el SO recuerda cada proceso

El PCB (Process Control Block) es la estructura de datos donde el kernel guarda todo lo necesario para pausar y reanudar un proceso.

Incluye: PID, estado actual, contador de programa, registros de CPU, límites de memoria, prioridad y lista de archivos abiertos.

Al cambiar de proceso, el SO guarda el PCB del que sale y carga el del que entra — eso es una conmutación de contexto.

1.2 Procesos y multiprogramación

Proceso pesado vs. hilo

Proceso pesado
  • Espacio de memoria propio y aislado.
  • Comunicación entre procesos requiere IPC (pipes, sockets, memoria compartida).
  • Cambio de contexto más costoso.
  • Mayor aislamiento: si uno falla, no arrastra a los demás.
Hilo (thread)
  • Comparte espacio de memoria con otros hilos del mismo proceso.
  • Comunicación directa mediante variables compartidas.
  • Cambio de contexto más ligero.
  • Menor aislamiento: un hilo corrupto puede afectar a todo el proceso.

1.2 Modelos de multiprogramación

Dos formas de repartir la CPU

Preventiva (por conmutación)
  • El SO interrumpe un proceso al agotarse su quantum de tiempo.
  • Un proceso mal comportado no puede bloquear al resto.
  • Modelo de todos los SO de servidor y escritorio modernos: Linux, Windows Server.
Cooperativa
  • Cada proceso debe ceder el control voluntariamente.
  • Un proceso mal comportado puede congelar todo el sistema.
  • Modelo histórico (Windows 3.x, Classic Mac OS); hoy sobrevive dentro de runtimes async de una sola aplicación.

Ejemplo resuelto

Inspeccionar procesos y estados reales

bash — servidor Linux
# Ver procesos con su estado (columna STAT)
$ ps aux | head -5
USER   PID  %CPU %MEM STAT  COMMAND
root     1   0.0  0.1  Ss    /sbin/init
www-data 482  0.3  1.2  S     nginx: worker process
mysql    901  1.1  4.8  Sl    mysqld

# S=espera interrumpible, R=ejecutable, D=espera no interrumpible, Z=zombi

# Ver los hilos de un proceso concreto
$ ps -eLf | grep mysqld | wc -l
24  # mysqld corre 24 hilos dentro de un solo proceso

# Ver conmutaciones de contexto acumuladas
$ vmstat 1 3

Caso de estudio

Cuando un proceso no termina de terminar

Incidente operativo

Un proceso zombi ya terminó su ejecución, pero su entrada en la tabla de procesos permanece porque el proceso padre no ha leído su código de salida con wait().

Un servidor con un demonio mal programado que no cosecha a sus hijos puede acumular miles de procesos zombi hasta agotar la tabla de PID del sistema.

No consumen CPU ni memoria significativa, pero sí agotan identificadores de proceso — un recurso finito que puede tumbar servicios nuevos si no se atiende.

Práctica de laboratorio 1 · Programa TSO

Reforzar multiprogramación con código

Individual Duración estimada: 45 min · Entregable: código fuente + reporte
  1. Escribe un programa en C o Python que cree un proceso hijo con fork() / multiprocessing.
  2. Escribe una segunda versión equivalente usando hilos (pthread / threading).
  3. Mide y compara el tiempo de creación de 100 procesos vs. 100 hilos.
  4. Observa con ps o el Administrador de Tareas el estado de cada uno mientras corre.
  5. Documenta en el reporte por qué el hilo fue más rápido de crear.
Criterios de evaluación: código funcional en ambas versiones (40%) · medición correcta de tiempos (30%) · explicación técnica de la diferencia (30%).

¿Qué información guarda el PCB de un proceso?
PID, estado, contador de programa, registros de CPU, límites de memoria, prioridad y archivos abiertos, entre otros.
¿Cuál es el riesgo principal de la multitarea cooperativa?
Un proceso mal comportado que no cede el control voluntariamente puede congelar todo el sistema.
¿Qué es un proceso zombi y por qué es un riesgo en producción?
Un proceso terminado cuyo padre no ha leído su código de salida; acumula entradas en la tabla de procesos y puede agotar los PID disponibles.

Cierre

En cinco ideas

  • Un proceso es un programa en ejecución con su propio contexto: memoria, registros y estado.
  • El PCB permite al SO pausar y reanudar procesos mediante conmutación de contexto.
  • Los hilos comparten memoria y son más ligeros de crear que los procesos pesados.
  • La multitarea preventiva domina en servidores; la cooperativa depende de la buena conducta del proceso.
  • Procesos zombi y huérfanos son fallas de gestión de ciclo de vida, no errores de hardware.
